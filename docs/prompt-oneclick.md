# 一键提示词（给不懂技术的人用）

> 把**本文档全部内容**复制给支持本地文件操作的 AI 助手（WorkBuddy 等），
> 它就会自己完成：探测环境 → 取密钥 → 解密 → 找到联系人 → 导出可搜索的网页版聊天记录。
> **使用者不需要懂技术，也不需要敲任何命令。**
>
> 本文档已把 `docs/pitfalls.md` 里踩过的坑全部前置，照着跑通常一趟就能过。

## 第一步：确认这 4 个前提

| | 前提 | 说明 |
|---|---|---|
| 1 | **Windows 电脑** | 不支持 Mac，也不支持手机 |
| 2 | **电脑上装了会用本地文件的 AI 助手** | 如 WorkBuddy；会用粘贴文字就行，不需要懂技术 |
| 3 | **电脑版微信已登录你自己，且正在运行** | 取密钥依赖运行中的进程，先别关 |
| 4 | **（想读完整历史）先把手机聊天记录迁到电脑微信** | 见下方说明 —— **这一步很多人会漏** |

> 只想导出手机里的记录、或用的是 Mac —— 这套方法不适用，不用往下试了。

### 第 4 条怎么做：把手机聊天记录迁到电脑

**为什么必须做这一步？**
电脑版微信**不会保存历史消息**，它只接收你登录期间的新消息。所以你刚登录电脑微信时，只能看到最近的一小段，更早的记录是空的。
**这不是故障，是微信本来的设计** —— 想要完整记录，必须从手机搬一次。

**怎么操作**（在**手机**微信上）：

1. 手机和电脑**连同一个 WiFi**（用电脑连手机热点常常失败，别这么干）。
2. 手机微信 → **我 → 设置 → 通用**（有的版本叫「聊天」）→ **聊天记录迁移与备份** → **迁移** → **迁移到电脑微信**。
3. 选择要迁移的聊天（第一次建议选「全部」）和时间范围 → 开始。
4. 保持网络连接、别关微信，等它传完。
5. 传完后，**去电脑微信里确认**一下：更早的消息是不是真的出现了。

### ⚠️ 千万别做错：有两个长得很像的功能

| 功能 | 在哪操作 | 结果 |
|---|---|---|
| **迁移到电脑微信** ✅ | **手机**上（设置 → 通用 → 聊天记录迁移与备份 → 迁移） | 记录真正进入电脑微信，**能被读到** |
| 备份聊天记录到电脑 ❌ | **电脑**微信左下角（更多 → 备份与恢复） | 只生成一个微信专用备份文件，**只能恢复到手机**，电脑微信自己读不了 |

**认准手机上的那个「迁移到电脑微信」。** 按错了就是白忙一场 —— 电脑微信里依旧没有历史记录。

## 第二步：怎么用

1. **全选复制本文件的全部内容**（按 `Ctrl + A`，再按 `Ctrl + C`）
   —— 记得复制**到底**，不要只复制开头。
2. **粘贴发给 AI 助手**（也可以直接把本文件拖进对话窗口）。
3. **只改下面这一行**，写上你想读的人或群（**备注 / 昵称 / 名字 / 微信号 / 群名，任意一个你知道的写法都行**）：

   > **我要读取的联系人：【在这里填 ta 的名字】**

4. 之后它会自己跑完。**中途可能会请你把微信关掉一次**（为了确保不漏掉你最近刚聊的内容），照做就行。

**大概要多久**：通常几分钟；聊天记录特别多时会久一些。**中途它会一直报进度**，看到它在跑就不用担心中途卡住。
**最后你会得到**：一个网页文件，双击就能打开，可以搜索、可以只看某一个人说的话、按日期排好。另外还会附三个数据文件（用 Excel 或程序打开用）。

## 第三步：关于安全（请一定看一眼）

- 全程**只在你自己这台电脑上**完成，**不会把任何内容上传到网上**。
- **只读取、不修改**你的微信原始数据，你的微信不会受任何影响。
- 但它会在你电脑上生成一份**聊天记录的明文副本**。这份文件包含全部聊天内容，所以：
  **请不要上传到网盘、不要发给别人。** 不想要了，直接删掉那个文件夹就行。

## 以下内容请连同上面一起发给 AI 助手（不要自己删改）

### 任务

帮用户读取他与【上方指定联系人 / 群】的微信聊天记录，跑通整条读取链路，并导出成可读文件：

1. `chat_<名字>.html` —— 单文件 HTML 阅读版（可搜索、可按发言人筛选、按日期分组、米色纸感、衬线标题）
2. `chat_<名字>.md` / `.csv` / `.jsonl` —— 分别供人阅读 / Excel 筛选 / 程序使用

**本次的范围**：只保证把"读取电脑版微信聊天记录"这条链路完整跑通并导出一份可读成品。

- **不负责下游任务**：不要去做情感分析、关系总结、聊天统计、群成员名单整理这类事。如果用户中途提这类要求，告诉他"这次先保证把记录完整读出来，分析类的需求可以之后另说"。
- 个人聊天是主要目标；**群聊原理相同**（表名规则一样），但群发言人更多、发送者映射更复杂，需要额外核对人名。

### 你必须先知道的用户情况

- **用户完全不懂技术。** 请不要把技术选择抛给他，不要让他手动执行任何命令。用大白话汇报进度。
- **开始前先用一两句话说明你要做几件事、大概多久**，让他心里有数。
- **产出文件请放在他容易找到的位置**（例如桌面上新建一个文件夹），最后把**完整路径**告诉他，并主动帮他打开那个网页文件。
- 只有在"确认要读谁"或"需要他做一次手动操作（如管理员权限、关闭微信）"时，才去问他。

### 硬性规则

- **全程只读原始数据。** 解密结果只写入副本目录，绝不修改或删除微信的原始文件。完成后明确告诉用户"你的微信原始数据一个字节都没有改动"。
- **不要照抄任何路径、wxid、数据库名** —— 一律先探测。
- **先看适用范围**：如果不是 Windows、或本机没有可读取的微信登录数据，**立刻告诉用户这套方法不适用并停止**，不要硬试。
- **如果找不到指定联系人，停下来告诉他**探测结果，不要猜测、不要随便挑一个会话。
- **任何一步失败都不要静默结束。** 要么给出下一步可执行的做法，要么明确告诉用户"请把下面这段报错原样发给助手"，并附上你看到的原始报错。用户遇到失败会直接放弃，所以这一步很重要。
- **凡是耗时超过十几秒的步骤，都要持续打印进度**（扫描内存、解密大库）。用户看不到进度就会以为卡死，然后强行中断。

### 第 0 步：探测

- 微信版本与安装路径；数据根目录（新版 4.x 是 `xwechat_files`，旧版 3.x 是 `Documents/WeChat Files`）。
- 当前活跃账号（数据根下形如 `wxid_xxx_abcd` 的目录即账号目录）。如果本机有多个账号，告诉用户你找到了哪几个。
- 数据库位置：账号目录下 `db_storage/`，含 `contact/contact.db`、`session/session.db`、`message/message_*.db`、`sns/sns.db` 等。
- **确认微信正在运行**（取密钥依赖运行中的进程）。如果没在运行，请用户先打开微信并登录。
- **顺手判断一下数据量是否偏小**：如果 message 库很小、消息总条数很少，很可能是用户**没有做"手机迁移到电脑微信"**（前提条件 4）。这时如实告诉他："你电脑微信里只有最近的消息，想要完整历史，需要先在手机上把聊天记录『迁移到电脑微信』，然后再跑一次这个流程。"

验收：能列出全部 `.db` 文件清单，并报出微信版本号。

> **版本提示**：本方法在 **微信 4.1.x** 上验证通过。如果你发现本机版本与 4.1.x 差别很大（尤其旧版 3.x），密钥获取方式可能完全不同 —— 先去搜索该版本对应的办法，或直接告诉用户"你的微信版本较新/较旧，这套方法可能不适用"。

### 第 1 步：取数据库密钥（关键步骤，别走弯路）

这批数据库是 **SQLCipher4 加密**的，文件头不是 `SQLite format 3`，**直接读不了**。密钥必须从**运行中的 Weixin.exe 进程内存**里取。

**以下四点就是这条路的全部难点，务必按此做，否则会反复失败：**

1. **密钥不以明文存在内存里。** 内存里存的是 keyspec 文本 `x'<64位hex的enc_key><32位hex的salt>'`，但它被一个 **32 字节的 pad 按周期 XOR 混淆**了。所以**直接搜 `x'<长hex>'` 会 0 命中 —— 别在这上面浪费轮次**（这是最常见的第一个坑）。

2. **用「已知明文」反推 pad。** keyspec 明文结构固定为 99 字节：
   - `[0:2]` = `x'`
   - `[2:66]` = enc_key 的 64 位 hex（小写）
   - `[66:98]` = 该库 salt 的 32 位 hex（小写）
   - `[98]` = `'`

   其中 **`[66:98]` 的明文是已知的** —— 它就是该数据库文件**前 16 字节（salt）的 hex**。拿它当已知明文即可当场反推 32 字节 pad：

   ```
   temp = ct[66:98] ^ salt_hex            # 得到 pad[2:32] ++ pad[0:2]
   pad[0:2]  = temp[30:32]
   pad[2:32] = temp[0:30]
   自校验： ct[0] ^ pad[0] == 'x'  且  ct[1] ^ pad[1] == "'"
   ```

   解出明文后，`pt[2:66]` 就是 32 字节 raw key。

   扫描加速写法：令 `diff[j] = mem[j] ^ mem[j+96]`，则密钥起始处满足 `diff[j] == 'x' ^ pad[0]` 且 `diff[j+1] == "'" ^ pad[1]`；而 pad[0]、pad[1] 可由该库的 `salt_hex[30]`、`salt_hex[31]` 直接推出（这两个字节在 keyspec 尾部明文里已知）。

3. **验证不能用 `SQLite format 3` 魔数。** 因为 SQLCipher 的 **page 1 前 16 字节被 salt 覆盖**，解密后开头本来就不是魔数（第二个大坑）。正确判据是：
   - 解密后 `pt[0:2]` 是合法页大小（大端），且 `pt[5:8]` 等于字节 `0x40 0x20 0x20`；
   - 并且页尾 64 字节的 **HMAC-SHA512** 与实算值一致。

4. **取到的 64 位 hex 就是可直接使用的 raw key**，**不要再跑 256000 轮 PBKDF2**（那是 passphrase 路线才需要的）。只有校验用的 MAC key 才需要派生：`mac_key = PBKDF2-SHA512(enc_key, salt逐字节异或0x3A, 2 轮, dklen=32)`。

**页结构参数**（SQLCipher4 默认，本方法已验证）：`page_size = 4096`、`reserve = 80`（= 16 字节 IV + 64 字节 HMAC），**IV 位于页内偏移 4016**（即 `page_size - reserve`）。

**扫描内存时的实现要点**（这些不注意会"静默少取到密钥"，很难排查）：

- **扫描所有 `Weixin.exe` 进程**，不只主进程 —— 密钥可能挂在子进程里。
- **分块读取内存时必须有重叠**（建议 256 字节以上）。否则跨块边界的 keyspec 会被截断，导致**部分库取不到密钥**。
- 只扫描 `MEM_COMMIT`、可读保护位、且未设 `PAGE_GUARD` 的内存区域。
- **不断打印进度**（如"已扫描 XX MB / 找到 N 个密钥"）。内存可能有好几 GB，要跑几分钟。
- **要处理 `db_storage` 下全部加密库**（不止 message），**每个库的 salt 不同**，要逐个匹配。
- 如果 `OpenProcess` 或 `ReadProcessMemory` 失败、但权限看起来正常，**考虑是杀毒软件拦截了"读取其他进程内存"这个动作**，请提示用户把助手程序加入白名单后重试。
- 取到密钥后**立刻落盘保存**（如 `keys.json`）—— 下一步用户会关闭微信，届时内存里的密钥就没了，必须先把密钥存下来。
- 读进程内存需要**管理员权限**。如果 `OpenProcess` 失败（返回 0），**不要静默失败** —— 请明确告诉用户："请把助手程序关掉，然后右键图标选择『以管理员身份运行』重新打开，再把这个文档发我一次。"并等他操作完成。

验收：**全部数据库**密钥都提取出来，且能成功解密各自 page 1。

### 第 2 步：关掉微信（可选但要跟用户确认），然后解密

微信的数据库开着 **WAL 模式**，同目录会有 `xxx.db-wal`、`xxx.db-shm`。
**实测结论：主库本身就是最新的**，WCDB 会自动 checkpoint（`-wal` 到 1000 页 ≈ 4MB 就刷回主库），
所以**不需要**单独解密 WAL。为稳妥起见可以多做一个**零成本保险**：

**顺序（不能换）：**

1. **先从内存取出密钥并保存到磁盘** —— 此时微信必须还在运行，这是取密钥的唯一时机。
2. **再请用户把微信完全退出。** SQLite 在最后一个连接关闭时会把 WAL 收尾合并回主库。
   请说明原因（"为了确保不漏掉你最近刚聊的内容，请先把微信关掉，我不会动你任何原始文件"），并等他关好再继续。
   > 如果用户不方便关（比如正在用），**可以直接解密**，实测数据也是最新的；只是万一后面发现少了最近几条，
   > 再补一次"关微信 → 重新解密"即可。
3. **然后才开始解密**主 `.db` 文件。

**解密范围可以按需取舍，不必全解：**

- **必须解**：`contact/contact.db`、`session/session.db`、`message/message_*.db`（**全部分片，一个都不能少**）。
- **可以跳过**：`*_fts.db`（全文索引，实测可达 **1.3GB**，解密又慢又占空间，导出用不上）、以及 `emoticon/`、`hardlink/`、`head_image/`、`favorite/`、`bizchat/`、`chatbot/` 等。
- 跳过之前先报一下待解密的总大小，避免在用户电脑上凭空多占好几个 GB。

**解密算法：**

- page 1：密文从偏移 16 开始（前 16 字节是 salt），IV 取页内偏移 4016，解密后需**人为补回** `SQLite format 3` 文件头（16 字节）再拼接明文。
- page 2 及之后：密文从偏移 0 开始，IV 同样取偏移 4016。
- 每页解密后把尾部 80 字节（IV + HMAC）用 0 补齐，凑满 4096 字节。
- 同样**打印进度**（大库几百 MB，需要时间）。

验收：解密后的库文件**头部必须是 `SQLite format 3`**，且能被 SQLite 正常打开、读到表。

### 第 3 步：找到要读的人

- 先在 `contact.db` 里按备注 / 昵称 / 微信号搜索。
- **搜不到是正常的** —— 对方可能压根没存备注。这时改用：在**解密后的全部数据里按内容检索**这个名字，反查它出现在哪个会话里，从而拿到 wxid（这个办法很有效，别忽略）。
- 交叉验证：`session.db` 的会话列表、`Name2Id` 映射、朋友圈 `sns.db` 都有线索。
- **如果匹配到多个或零个**，请把最可能的几个会话列给用户选（附上昵称、微信号、以及最近的几条聊天摘要），让他点一下就行 —— 不要让他去想 wxid 这种概念。
- **确认后向用户核对一次**再继续。找不到就停下汇报。

### 第 4 步：读取并导出聊天记录

- 消息表名 = **`Msg_<md5(会话wxid)>`**（md5 为该 wxid 的小写十六进制；群聊同理，用群 id）。
- 消息**分片**存放在多个 `message_*.db`，**要扫描目录下实际存在的全部分片再合并**（不要写死成 4 个，不同版本数量不同）。
- **最大的坑：每个分片的 `Name2Id` 表是独立的。** 必须**按分片各自**解析发送者编号，否则人名会整体错位（务必单独核对这一点）。
- 时间字段是 Unix 秒；类型字段 `local_type` 取其**低 32 位**（`local_type & 0xFFFFFFFF`）；正文可能被 **zstd 压缩**（判据：`WCDB_CT_message_content == 4`），需要解压。
- 自己发的消息判定：`real_sender_id == 1`，或发送者映射到自己的 wxid。
- 跨分片合并后做**指纹去重**（同一条消息可能在多个分片重复），指纹用 `(时间, 说话人, 内容摘要)` 即可。
- 消息类型映射：`1` 文本 / `3` 图片 / `34` 语音 / `42` 名片 / `43` 视频 / `47` 表情 / `48` 位置 / `50` 通话 / `49` appmsg（看 XML 里的 `<appmsg><type>`：`6` 文件、`5` 链接、`57` 引用、`33/36/44` 小程序）/ `10000` 系统提示 / `10002` 撤回。
- **引用消息**（appmsg type = 57）要把 `<refermsg>` 里的原文和被引用人摘出来，**别把 XML 原文直接塞进正文**（否则可读性极差）。

验收：打印出发送者分布（自己 / 对方各多少条）与时间范围，两者看起来合理。

### 第 5 步：产出

- 生成**单文件 HTML 阅读版**：微信风格气泡（自己右侧、对方左侧）、按日期分组、顶部搜索框、可按发言人筛选、米色纸感 + 衬线标题，优雅耐读。
- 同时导出 `.md`（人读）、`.csv`（Excel 筛选）、`.jsonl`（程序用）。
- **CSV 必须用带 BOM 的 UTF-8（`utf-8-sig`）写入**。否则用户用 Excel 打开会**满屏中文乱码**，这是大众最常遇到的"看起来坏了"。
- 把全部文件放到一个容易找到的文件夹里，用对方的名字命名。

### 最后的汇报

- 每完成一步用一两句话说明结果（例如"找到 26 个数据库密钥，全部验证通过"）。
- 最后汇报：**读的是谁**（昵称 / 微信号）、**消息总数**、**时间跨度**、**文件完整路径**。
- **务必做一次自检**：看看导出的**最后一条消息距今多久**。如果用户最近还在一起聊天，而这个时间差了好几天，说明很可能有数据没合并进来。这时**不要直接把成品交付**，告诉用户并重走"关微信 → 重新解密"的流程。
- 主动说明数据本身的限制：**语音、视频本地没有文字内容**，图片等以 `[图片]` 占位。
- 提醒用户：这份副本包含全部聊天内容，**不要上传网盘或发给别人**。

### 卡住时的自救办法（最容易卡在第 1 步）

如果取密钥反复失败，**不要硬试**。改去搜索以下关键词，或直接参考现成实现：

- `微信 4.x 数据库密钥 XOR keyspec 已知明文`
- `wcdb Config.Cipher runtime key windows`
- `wechat 4.0 sqlcipher page size 4096 reserve 80 hmac sha512`
- 参考实现仓库：`github.com/lzhdelife/wechat-archive-pipeline`
  （若本机 GitHub 直连不通，可用 `https://cdn.jsdelivr.net/gh/lzhdelife/wechat-archive-pipeline@main/<文件路径>` 拉取源码）

如果确认是微信版本差异导致的方法失效，**如实告诉用户"微信更新后这个方法暂时失效了，请把这段话反馈给作者"**，不要给他一个半成品。

### 边界

- 仅用于读取**用户本人**在本机的聊天记录。**不要**用它读取他人的数据。
- 读取需要管理员权限；密钥与本次登录绑定，**微信退出重登后需要重新提取一次**（也就是**每换一次登录，都要重新跑一遍这个流程**）。
