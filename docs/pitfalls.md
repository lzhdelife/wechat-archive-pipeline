# 踩坑清单（14 条，全部实测）

> 本文档是这套流水线最值钱的部分。每一条都是真金白银试出来的。

---

## 1. 4.1+ 内存里没有明文密钥，旧工具全部失效

**现象**：早期工具在进程内存里扫 `x'<64位hex>'` 形式的明文密钥，4.1 之前一直好用。

**4.1 之后**：内存里不再缓存明文密钥，只留一个 passphrase。所有基于内存模式扫描的工具（如 `328336690/wechat-decrypt`）直接归零。

**结论**：别浪费时间在内存扫字面量上。要么走运行时对象（本仓库方案），要么走 Hook（有风险）。

---

## 2. 密钥是 XOR 混淆的，必须"以对象视角"读

**现象**：即使用更强的特征去扫内存，也找不到可用密钥。

**原因**：4.1 把密钥放在一个运行时配置对象（`Config.Cipher`）里，且做了 XOR 混淆。

**关键认知**：不能以"字节视角"扫，要以"对象视角"读——先定位对象，再按对象结构取出字段，最后 XOR 解码。

> 补充（第二轮实测）：也可以完全绕开对象结构，用"已知明文反推 pad"的办法扫整块内存。见坑 12。

---

## 3. 同一个消息表在多个分片里都存在

**现象**：用 `Msg_<md5(id)>` 找表，会在 `message_0.db` ~ `message_4.db` 里都命中。

**原因**：微信按时间/容量对消息分片存储，同一个会话的表名在多个分片里都会出现。

**解法**：跨所有分片合并，并按**内容指纹**（`sha1(time|sender|type|content)`）去重。

---

## 4. ⚠️ 各分片的 Name2Id rowid 独立，会冲突

**这是最危险、最难自己发现的坑。**

**现象**：`real_sender_id` 需要查 `Name2Id` 表映射到真实 wxid。

**陷阱**：每个分片有**自己的** `Name2Id` 表，rowid 完全独立——

```
message_0.db:  rowid 2 → wxid_AAA
message_1.db:  rowid 2 → wxid_BBB     ← 同一个 2，指向不同的人
```

**后果**：如果你合并时共用一份映射，**所有消息的发送者归属全部错乱**。
最可怕的是——**导出的数据看起来完全正常**，只是人名全错，不逐条核对根本发现不了。

**解法**：解析每个分片时，**必须用该分片自己的 `Name2Id` 映射**。

**自检方法**：导出后检查"我 / 对方"的条数比例是否合理；异常大概率就是这个坑。

---

## 5. `local_type` 高 32 位存了子类型

**现象**：`local_type` 出现 `25769803825`、`244813135921` 这种巨大的数。

**原因**：4.x 把子类型塞进了高 32 位。

**解法**：判断类型前先掩码 `local_type & 0xFFFFFFFF`。

---

## 6. 内容存在 `message_content`，且可能被 zstd 压缩

**现象**：读出来的内容是 `b'(\xb5/\xfd...'` 这样的二进制乱码。

**原因**：`WCDB_CT_message_content == 4` 表示内容是 zstd 压缩的。

**解法**：
- 判断压缩标志或魔数 `\x28\xb5\x2f\xfd`
- 用 `zstandard` 解压
- **注意**：缺 `zstandard` 依赖时务必显式报错，否则会静默产出乱码

---

## 7. 引用消息的原文被 HTML 转义

**现象**：引用消息里读出来是 `&lt;title&gt;` 这种。

**解法**：先 `html.unescape()` 再剥 XML 标签。

---

## 8. `<refermsg>` 里也含 `<title>`

**现象**：取消息主标题时，取到了被引用消息的短标题。

**原因**：正则 `<title>(.*?)</title>` 会先匹配到 `<refermsg>` 内部的 `<title>`。

**解法**：取主标题前**先剔除整个 `<refermsg>` 块**。

---

## 9. WAL：不需要单独解密，但"先取密钥、再关微信、后解密"的顺序是零成本保险

**现象**：`db_storage` 目录下每个 `.db` 旁边都躺着一个同名的 `-wal`、`-shm`，
其中 `-wal` 常有 4MB 左右、时间戳是**刚刚**。于是担心："最新消息是不是还在 WAL 里，只解密主库会漏？"

**实测结论（两轮，独立验证）：不需要单独解密 WAL。**
主库解密出来就是最新的：

| 验证 | 结果 |
|---|---|
| `session.db` 的 `last_timestamp` vs 消息表 `MAX(create_time)` | **差值 0 秒** |
| 只解密 `message_2.db`（不含 `-wal`）拿到的全局最新消息 | **距今 2.2 分钟**，与 `-wal` 的 mtime 同步 |

**原因**：WCDB 开着 **auto-checkpoint**，阈值 1000 页 —— 两个 `-wal` 文件大小都**恰好是 4194304 字节 = 1024×4096**，
说明它一到阈值就把 WAL 刷回主库，所以主库与 WAL 基本同步。

**但仍有极小的"尾巴窗口"**：最后一次 checkpoint 之后、尚未刷盘的少量写入。
概率低，代价却是"用户以为备份漏了最新的几条"。所以推荐这个**顺序**（顺序不能换）：

1. **先**从运行中的进程取密钥并落盘 —— 这是取密钥的**唯一时机**，微信必须还在跑；
2. **再**请用户把微信**完全退出**（最后一个连接关闭时 SQLite 会收尾 checkpoint，WAL 并入主库）；
3. **最后**才开始解密。

> 也就是：**关微信不是解密的前置条件，而是"保险动作"**；但一旦关掉微信，密钥就取不到了，
> 所以"先取密钥"这一步绝不能和它调换顺序。

**交付前自检**：看导出的**最后一条消息距今多久**。用户今天还在聊天、而时间差了好几天，
就不要直接交付，重走一遍"关微信 → 重新解密"。

---

## 10. 手机记录要在电脑上，"迁移"而非"备份"

**现象**：手机上记录很全，电脑上却很少。

**原因**：微信电脑版不会自动同步全部手机记录。

**解法**：手机微信 → 我 → 设置 → 聊天 → **聊天记录迁移与备份** → **迁移到电脑**。

**关键区别**：
- **迁移** = 合并进电脑数据库（可读）✅
- **备份** = 生成加密包（读不了）❌

---

## 11. ⚠️ 页 1 前 16 字节被 salt 占着，别拿 `SQLite format 3` 当判据

**现象**：密钥明明是对的，但用它解密第 1 页后**看不到** `SQLite format 3\0`，
于是误判"密钥取错了"，回头反复重扫内存 / 重取密钥，白折腾半天。

**原因**：SQLCipher 会把数据库**前 16 字节的头部**替换成本库的 salt。
解密第 1 页后，`pt[0:16]` 是 **salt 本身**，不是 SQLite 魔数。
明文 SQLite 文件的魔数需要**人为补回**——这正是解密器第 1 页写
`SQLITE_HDR + pt + b"\x00" * RESERVE` 的原因，不是可选的美化。

**正确判据**（满足其一即可，两个都过最稳）：

1. **页头字段**：解密 page1 后
   - `pt[0:2] == \x10\x00` → page_size = 4096（大端）
   - `pt[5:8] == \x40\x20\x20` → SQLite 文件头余段固定值
2. **HMAC-SHA512**：
   ```python
   mac_salt = bytes(b ^ 0x3A for b in page1[:16])
   mac_key  = hashlib.pbkdf2_hmac("sha512", enc_key, mac_salt, 2, dklen=32)
   hm       = hmac.new(mac_key, page1[16 : 4096-80+16], hashlib.sha512)
   hm.update(struct.pack("<I", 1))
   assert hm.digest() == page1[4096-64 : 4096]
   ```

**别混淆两个 PBKDF2**：
- 上面这步是 **MAC key** 派生，**2 轮**迭代（SQLCipher 规范）；
- 而"enc key 的 256000 轮 PBKDF2"只在**passphrase 路线**（Linux/macOS 断点）用；
- **raw key 路线**（`x'<64hex>'`，Windows runtime 扫描走的就是它）对 enc key 不做任何 PBKDF2。

## 12. 4.1 的 keyspec 是 XOR 混淆的——用"已知明文"现场反推 pad

**现象**：内存里连 `x'<64hex>'` 都扫不到，直接 0 命中（坑 1 的后续）。

**原因**：4.1 把整串 keyspec

```
x'<64位 enc_key 的 hex><32位 salt 的 hex>'      # 共 99 字节
```

用一个 **32 字节 pad 循环 XOR**（`keyspec[j] ^= pad[j % 32]`）混淆后，放进运行时对象里。

**解法（`tools/lite/wcdb_key_lite.py` 用的就是这个，不依赖对象结构、也不依赖版本相关的掩码常量）**：

keyspec **尾部 32 字节的明文就是该库 salt 的 ASCII hex**——这是**已知的**，于是可当场反推 pad：

```python
temp = bytes(a ^ b for a, b in zip(ct[66:98], salt_hex))   # = pad[2:32] ++ pad[0:2]
pad  = temp[30:32] + temp[0:30]                            # 旋转回正确相位
assert ct[0] ^ pad[0] == ord('x') and ct[1] ^ pad[1] == ord("'")   # 自校验
pt      = bytes(ct[j] ^ pad[j % 32] for j in range(99))    # 解出明文 keyspec
raw_key = bytes.fromhex(pt[2:66].decode())                 # 32 字节
```

全内存扫描时不必逐字节试：只在 `diff[j] = data[j] ^ data[j+96]` 上找
`(diff[j], diff[j+1]) == (ord('x') ^ pad0, ord("'") ^ pad1)` 这一个 2 字节特征即可，
一次大整数异或就能扫完几百 MB，很快。

**好处**：微信升级、掩码常量变化时依然可用——只要 keyspec 还带 salt 尾巴就行。

## 13. 对方不在联系人里时，怎么反查出他的 wxid

**现象**：想归档和某人的私聊，但把能想到的名字在 `contact.db` 的
`remark` / `nick_name` / `alias` / 拼音字段里搜了个遍都**搜不到**——
对方没被存成联系人备注，昵称也不是真名。于是不知道该往 `config_pm.json` 里填什么 `peer_wxid`。

**解法（用"内容反查会话"）**：

1. 在**已经解密**的明文数据里按字节搜名字：
   ```bash
   grep -rla "真名" data/decrypted/
   ```
   通常会命中 `message/message_N.db`、`sns/sns.db`（朋友圈）等；
2. 表名即 `Msg_<md5(对方wxid)>`。把命中该名字的会话表里的消息抽出来看
   ——往往是"**XXX 撤回了一条消息**"这类系统提示，或对方一句自述，
   足以认定身份；
3. 三重交叉核对：
   ```python
   hashlib.md5(peer_wxid.encode()).hexdigest() == "命中表名的后缀"
   ```
   再用该 wxid 到 `session.db` 的 `SessionTable` 查最近消息、
   到 `contact.db` 看 `alias`（微信号缩写常能印证真名，如 `AaLV…` = 吕）。

> 比"逐个会话点开猜"快得多，是"名字 → wxid"反查的标准姿势。

## 14. 解密范围要取舍：`*_fts.db` 可能有 1GB+

**现象**：`db_storage` 下 **26 个** `.db` 全都加密，无脑全解 —— 又慢、又凭空多占几个 GB。

**实测体积**（本机抽样）：

| 库 | 体积 | 导出是否需要 |
|---|---|---|
| `message/message_*.db` | 单库最大 **392 MB** | ✅ 必需 |
| `message/message_fts.db` | **1.3 GB** | ❌ 全文索引，导出用不上 |
| `contact/contact.db`、`session/session.db` | 几十 MB 内 | ✅ 必需 |
| `emoticon/`、`hardlink/`、`head_image/`、`favorite/`、`bizchat/`、`chatbot/` | 小 ~ 中 | ❌ 可跳过 |

**解法**：

- **必须解**：`contact/contact.db`、`session/session.db`、`message/message_*.db`（含全部分片）；
- **跳过**：`*_fts.db`（全文索引）及其余辅助库；
- 动手前**先报一下待解密总大小**，别在用户机器上悄无声息多占几 GB。

> 注意：**跳过的是解密，不是跳过 `message_*` 的任何分片** —— 少解一个分片就会真的丢消息（见坑 3）。

## 附：其他易踩点

| 坑 | 解法 |
|---|---|
| 取密钥工具 `-v` 参数位置 | 必须放在 `extract` 子命令**前面** |
| 密钥失效 | 每次登录可能变，失效就重新取 |
| 缺管理员权限 | 读进程内存需要管理员身份 |
| 微信未运行 | 取密钥前必须确保微信登录在线 |
| 新导入记录后旧密钥失效 | 数据库结构变了会新增库，需重取密钥 |
| 语音消息无内容 | 只有 aeskey + CDN 地址，本地无音频文件 |
| 判定密钥是否正确的依据 | 不是 `SQLite format 3`（见坑 11），是页头字段 + HMAC-SHA512 |
| 掩码常量随版本失效 | 改用"已知明文反推 pad"（见坑 12），无需版本相关常量 |
| 名字搜不到 / 不知 peer_wxid | 用解密数据 `grep` 名字反查会话表（见坑 13） |
| **只解密主库会漏最新几条？** | 实测不会（坑 9），但推荐"先取密钥 → 关微信 → 再解密"的顺序 |
| **全解一遍好几 GB、很慢** | 跳过 `*_fts.db` 等，见坑 14 |
| **消息分片数量** | 别写死 4/5 个，扫描目录下**实际存在**的全部分片（见坑 3） |
| **内存分块扫描要重叠** | 建议 ≥256 字节重叠，否则跨块边界的 keyspec 被截断 → **静默少取密钥** |
| **杀软拦截读进程内存** | 权限看起来正常却失败时，考虑加白名单后重试 |
| **扫描/解密没进度** | 大库要跑十几秒~几分钟，必须持续打印进度，否则用户以为卡死会中断 |
| **CSV 用 Excel 打开是乱码** | 用 `utf-8-sig`（带 BOM）写入 |
| **关微信的时机** | 必须先取密钥再关微信（坑 9）；关掉后密钥就取不到了 |
| **Mac 用户想照搬本仓库** | 不行：Mac 的机制不同（走 LLDB + 重新签名微信），见 [`macos.md`](macos.md) |
| **在 Mac 上做重新签名** | GreenBubbles 需要替换 `WeChat.app` 的苹果签名（**不动聊天数据**），微信升级后会恢复 |
